# План: постоянная резервная копия одного выбранного чата

Дата: 2026-09-09. Исходный план; реализация описана в README, раздел Permanent chat backups.

Уточнение владельца: архивируем два явно выбранных чата. Каждая команда
по-прежнему принимает один точный sourceId; каждый архив изолирован и постоянно
хранится на сервере. Внешняя копия дополняет локальную, а не заменяет её.

## Задача и границы

Владелец явно включает архивирование по точному `sourceId` конкретного чата.
Чаты без явного включения не архивируются, их настройки и поведение не меняются.
Все операции первой версии требуют один `sourceId`; нет выбора всех чатов,
масок, наследования по тегам или автоматического включения новых источников.
Конкретный ID потребуется при включении, для реализации плана он не нужен.

Архив сохраняет всё уже полученное даже после удаления сообщения, правки,
исчезновения чата, потери доступа или остановки индексации. Он должен позволять
восстановить данные и поиск без Telegram и без повторной транскрибации.

«Не удаляемый» означает: нет срока автоочистки, удаления вслед за Telegram,
перезаписи предыдущих версий или удаления через обычный purge. Защита от потери
сервера требует второй независимой копии; защита от удаления администратором
хранилища требует дополнительно настроенной блокировки удаления объектов.
Локальная папка сама по себе не обеспечивает этих двух гарантий.

Граница полноты: сохраняем ранее проиндексированное и всю историю, которую
Telegram ещё отдаёт этому аккаунту. Уже исчезнувший файл нельзя восстановить
из его метаданных или расшифровки. Сообщение, созданное и удалённое между
наблюдениями, может не попасть в архив. Все известные пробелы видимы в статусе.

## Что есть сейчас

- `src/storage/mongoStore.js`: `tg_messages` содержит текст, `transcriptText`,
  метаданные транскрибации и медиа. Повторный импорт обновляет сообщение через
  `$set`, сохраняя расшифровку, но не предыдущую версию текста.
- `src/telegram/telegramSync.js`: инкрементальный импорт новых ID с лимитом
  сообщений и `historyDepthDays`. Пропускаются некоторые типы сообщений и
  отключённые настройками replies/forwards/media.
- `src/telegram/sourceSyncCoordinator.js`: есть блокировки на источник;
  историческая загрузка также ограничена глубиной обычной индексации.
- `src/audio/transcriptionWorker.js` и `src/audio/audioService.js`: оригинал
  скачивается во временную папку и удаляется в `finally`.
- `src/images/imageCache.js`: отдельный кеш картинок с хранением до 30 дней.
  Текущий downloader выбирает наибольшую фотографию, помещающуюся в лимит;
  такой выбор нельзя считать гарантией максимального качества архива.
- `src/telegram/reactionWorker.js`: слушает изменения реакций, но не является
  универсальным журналом новых сообщений, правок и удалений.
- `purgeSourceData` удаляет сообщения, дайджесты и записи кеша; обычное чтение
  через `sourceAccess` требует enabled-источник.

Следствие: архиву нужны собственные данные, курсоры, хранение файлов и путь
чтения. Увеличить срок жизни текущего кеша недостаточно.

## Состав резервной копии

| Данные | Что сохраняем |
| --- | --- |
| Чат | ID, тип, название, username, наблюдавшиеся изменения, настройки и относящийся к чату аудит |
| Сообщения | ID, даты, текст, форматирование, доступные сведения об отправителе, ответы, пересылки, альбомы, темы и служебные сообщения |
| Изменения | Все наблюдавшиеся версии текста и вложений; события реакций и подтверждённых удалений с временем наблюдения |
| Расшифровки | Текст, модель, язык, сегменты, чанки, статус и ошибки; версии результатов, связанные с конкретным аудиофайлом |
| Картинки | Максимальная доступная версия Telegram photo; изображения, отправленные файлом, без преобразования |
| Аудио | Исходные voice/audio bytes без перекодирования, имя, MIME, длительность и размер |
| Другие вложения | Сохраняемый Telegram payload и оригинал, если скачивание поддерживается; неизвестные типы учитываются как пробел, а не исчезают из отчёта |
| Поиск и производные данные | Документы для поиска, описание индексов/версии схемы, сохранённые дайджесты только этого чата; индексы можно построить заново |

Не включать секреты приложения, Telegram session и данные других чатов.
Смешанные дайджесты нескольких источников не копировать в архив одного чата.
«Оригинал фото» здесь — максимально качественные доступные Telegram bytes;
файл до обработки Telegram не обещается. Telegram предоставляет несколько
вариантов фото и отдельные миниатюры: [Telegram Files API](https://core.telegram.org/api/files).

## Предлагаемая архитектура

1. **Политика одного чата.** Отдельная запись `tg_archive_sources`: `sourceId`,
   `captureEnabled`, время включения, состояние истории и курсоры. По умолчанию
   архивирование выключено. Состояния сбора: `backfilling`, `active`, `paused`,
   `source_unavailable`, `error`. Состояния полноты и внешней копии независимы.
2. **Постоянный журнал.** Версионированные неизменяемые записи в
   `/srv/tg-mcp/shared/chat-archive/<sourceId>/records/` и файлы в `blobs/`.
   MongoDB содержит рабочую проекцию для поиска и очередей, но не единственную
   копию метаданных. Формат — документированный JSONL/JSON с `schemaVersion`.
3. **Файлы по SHA-256.** Дедупликация внутри архива выбранного чата;
   связь `(sourceId, messageId, mediaVersion)` с хешем, размером и MIME.
   Имена пользователя не становятся путями. Запись через временный файл,
   проверку размера/хеша и атомарную публикацию; существующий blob не затирать.
4. **Очередь и контроль записи.** Идемпотентные задания, lease с продлением,
   повторные попытки и backoff. Курсор страницы продвигается только после
   надёжного сохранения записей и заданий медиа. Журнал позволяет пересоздать
   потерянную очередь; перезапуск между записью файла и Mongo не теряет данные.
5. **Вторая копия вне VPS.** Передавать blobs, записи, версии схемы и manifests
   в независимое хранилище. Снимок получает признак `verified` только после
   проверки наличия всех перечисленных объектов. Сохранять предыдущие снимки.
   Ошибка репликации не останавливает локальный сбор, но видна как отставание.

Mongo-проекции можно обновлять; ранее записанные архивные версии — нельзя.
История переходов A → B → A сохраняется как три наблюдения с двумя разными
payload-хешами. Повтор одного и того же события при retry не создаёт дубликат.
Замена аудио не должна прикреплять расшифровку старого файла к новому.

Кеш картинок и audio-work физически отделены от архива. Их уборщики не обходят
архивную папку. Перед повторным скачиванием допустимо перенести пригодный кеш
в архив, проверив соответствие версии и максимальному качеству фото.

## Первичное заполнение и дальнейший сбор

1. Проверить точный источник и существующий `ALLOWED_SOURCE_IDS`. Создать
   политику архива только для него; явно показать статус начала и дисковое место.
2. Сначала зафиксировать уже имеющиеся документы Mongo, включая расшифровки
   сообщений, которых больше нет в Telegram. Сохранить пригодные файлы кеша.
3. Зафиксировать верхнюю границу истории и параллельно начать сбор новых
   сообщений этого чата. Выгрузить старую историю страницами до её доступного
   начала, с устойчивым курсором и возобновлением после рестарта.
4. Полный архивный проход не ограничивать `historyDepthDays` и фильтрами
   `includeReplies/includeForwardedPosts/includeMedia` обычного индекса.
   Эти настройки обычного источника не менять. Размер страницы ограничивает
   одну порцию работы, а не общее количество сохранённых сообщений.
5. Для накопившихся новых сообщений проходить все страницы между курсором и
   зафиксированной верхней границей. Не передвигать курсор сразу к самому
   новому ID после одной ограниченной страницы: это может пропустить середину.
6. Скачивать оригиналы сразу после обнаружения; новые медиа приоритетнее
   исторической очереди. Транскрибация не блокирует сохранение оригинала.
   Лимиты архивных загрузок независимы от лимитов выдачи MCP и OpenAI.
   Превышение лимита — видимый `blocked_by_limit`, без подмены фото миниатюрой.
7. Добавить обработку new/edit/delete updates для этого source, восстановление
   соединения и периодическую сверку истории. Использовать общую координацию
   Telegram-запросов, чтобы архив, обычная синхронизация и транскрибация не
   устраивали конкурирующие неограниченные скачивания.
8. Удаление — новая запись с прежним содержимым на месте. Отсутствие сообщения
   в ограниченной выдаче или потерю доступа ко всему чату не считать удалением.
   Если update не позволяет однозначно определить чат, не относить его наугад.

Полноту старых правок задним числом не обещать: сохраняются только увиденные
версии. Недоступный чат переводится в `source_unavailable`; чтение архива
продолжает работать. Остановка обычного источника приостанавливает сетевой
сбор, но не удаляет и не скрывает архив от владельца.

Все существующие и новые результаты транскрибации сохраняются в журнале.
Для ещё не расшифрованного аудио предусмотреть отдельный явный запуск по
этому архиву с лимитом/бюджетом; включение backup само не запускает платную
расшифровку всей истории и не меняет текущие allowlists OpenAI.
Архивный запуск умеет читать сохранённый оригинал без Telegram.

## Чтение, защита и восстановление

- Отдельные owner API/MCP операции: `get_source_backup_status`,
  `search_source_backup`, `get_backup_message_context`, `get_backup_media`.
  Все требуют один точный `sourceId`; медиа выдаётся по выбранным ID/версиям.
- CLI: `backup-source <id>`, `backup-status <id>`, `pause-source-backup <id>`,
  `resume-source-backup <id>`, `verify-source-backup <id>`,
  `export-source-backup <id>`, `restore-source-backup <id> --target ...`.
  Сначала реализовать CLI/admin; управление через MCP — после базовой проверки.
- Отдельная проверка прав на архив: сохранённый архив доступен владельцу даже
  при disabled/исчезнувшем Telegram source. Hard ceiling сохраняется;
  его изменение может запретить чтение, но не удаляет сохранённое.
  OAuth: отдельные scopes `telegram:backup:read` / `telegram:backup:manage`
  с общей базовой авторизацией endpoint. No-auth MCP не получает архивных tools.
- `purge-source-data` блокируется для защищённого источника, в том числе после
  pause. Проверка на уровне storage/service, а не только CLI. Удаление архива
  не входит в первую версию; обычные cleanup/disable/purge не снимают защиту.
- Экспорт содержит manifest, записи/версии, media inventory, blobs, схему,
  определения поисковых индексов и список известных пробелов.
  Последовательность журнала задаёт согласованную границу снимка при активной
  записи; незавершённые медиа явно отмечены и не объявлены сохранёнными.
- Restore сначала выполняется в отдельную пустую БД/папку: проверить хеши,
  построить проекции и индексы, проверить поиск по тексту и расшифровкам,
  выдать исходные изображения/аудио. Живой источник автоматически не включать.
  Восстановление означает локальный архив, не повторную отправку в Telegram.

Для строгой защиты внешней копии предусмотреть хранилище с Object Lock и
отдельные права приложения без удаления/снятия блокировки. У S3 compliance
защита действует до заданной даты; legal hold не имеет срока, но может быть
снят уполномоченной ролью. Поэтому не обещать абсолютную вечную неуничтожимость.
Выбор хранилища и срока блокировки нужен перед его настройкой, а не для начала
реализации: [официальная документация Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

## Статус и эксплуатация

Показывать период доступной истории, окончание первичного прохода, количество
сообщений/версий, оригиналов и расшифровок, объём и свободное место; отдельно
`pending`, `failed`, `unavailable`, `unsupported`, `blocked_by_limit`.
Показывать время последнего наблюдения, последнюю проверку целостности,
последний подтверждённый внешний снимок и отставание репликации.
«История пройдена», «все известные медиа сохранены» и «копия вне сервера
проверена» — разные признаки. Не показывать 100% без известного знаменателя.

При заполнении диска остановить новые записи с явной ошибкой; не освобождать
место удалением старого архива. Оповещения: остановка сбора, потеря доступа,
ошибки файлов, недостаток места и отставание внешней копии. Периодически
проверять хеши и выполнять пробное восстановление внешней копии.

## Этапы реализации и проверка

1. **Хранилище и защита.** Новый `src/backup/`, политика, журнал, blobs,
   Mongo/memory-проекции, guard purge, независимые директории и конфигурация.
   Проверить идемпотентность, версии A → B → A, сбои записи, pause/disable/purge.
2. **Полная история одного чата.** Перенос существующего индекса, пагинация,
   отдельные курсоры, очередь оригиналов и прогресс; интеграция в server/CLI.
   Проверить историю старше обычного лимита, поток больше размера страницы,
   restart и отсутствие архивных данных/заданий для второго тестового чата.
3. **Непрерывное пополнение.** Новые сообщения/правки/удаления, сверка,
   архивирование результатов транскрибации. Проверить замену вложения, удаление
   до/после скачивания, FloodWait, reconnect, lease expiry и сбой OpenAI.
4. **Доступ без Telegram.** Архивный поиск, контекст, оригиналы, CLI/admin и
   MCP/OAuth/OpenAPI. Проверить disabled source, недоступный Telegram, scopes,
   hard ceiling и отсутствие tools/данных архива на no-auth endpoint.
5. **Настоящая резервная копия.** Экспорт, репликация, Object Lock при выбранной
   политике, verification и restore; эксплуатационная инструкция в README/ops.
   Проверить восстановление после потери локальных Mongo и archive root,
   используя только внешнюю копию, включая detection повреждённого blob.

После соответствующих изменений запускать целевые Node-тесты, затем `npm test`.
Интеграционные проверки Mongo, файлового хранилища и restore обязательны:
одних memory mocks для гарантии восстановления недостаточно.

Критерий готовности всей фичи: для выбранного тестового чата сохранить историю,
правку, картинку, аудио и расшифровку; удалить сообщения в Telegram; выполнить
обычную очистку кеша; отключить Telegram; восстановить из внешней копии в пустое
окружение и найти сообщения/обе версии, прочитать расшифровку и получить файлы
с исходными хешами. Второй чат во всех проверках остаётся вне архива.
